01 · Architecture and implementation

Ordered synchronization from SAP to SaaS

I redesigned SAP-to-SaaS processing around ordered object queues. Dependent updates stay in sequence while independent queues run in parallel. Failed units retry in place, and unchanged PUT payloads skip the outbound request.

Problem
The architecture was not Clean Core compliant. Initial and delta loads were slow, especially for materials and invoices. Errors were never retried, so brief outages or temporary errors failed entire units. There was no versioning: only the active time period was considered, leaving future-dated updates unhandled. Every SAP update triggered a service call, even when the SaaS data stayed unchanged, increasing service load and customers’ middleware costs.
My work
Replaced direct database reads with SAP interfaces and ordered parallel queues. Added retries, version handling for current and future periods, caching, and PUT payload hashing.
Result
Clean Core B compliant processing with faster initial and delta loads, recovery from temporary failures, and ordered future-dated updates. Unchanged PUT payloads skip outbound calls, reducing service load and middleware traffic.

How synchronization worksDependencies, retry behavior, and PUT change detection.
  1. BAPI, IDoc, output messages, BOR, and CDS views feed the object queues.
  2. A queue can contain multiple object types. In this example, the supplier resolves before the purchase order in the same queue.
  3. A failed unit retries in place and blocks later units in that queue. Independent queues can continue.
  4. Successive field or version changes to one object remain ordered, as shown by the cost-center example.
  5. Before a PUT, compare the object's payload hash with its last successful outbound update. Identical content skips the request and completes the unit. Changed content or a missing baseline sends the PUT.
  6. A successful PUT saves the new hash. Failure retains the previous baseline so the update remains eligible for retry. Other HTTP methods bypass this PUT-specific check.

02 · Agentic expense workflow

Configure and track how an expense agent interacts with SAP

I built an SAP application to configure and track how an agentic expense workflow interacts with the system. It brings workflow configuration, execution logs, parallel queues, expense details, and FI/HCM posting status into one workspace.

Problem
The agentic SaaS worked as intended, but the customer had no clear view of the agent’s actions or their status in SAP.
My work
Built an SAP application combining agent configuration, execution logs, queue visibility, expense details, and FI/HCM posting status, with links to the underlying SAP records.
Result
Customers can follow the agent’s actions, see their status, and investigate errors from one workspace.
Workflow configuration and execution trackingAgent settings, execution logs, queues, and SAP processing outcomes.
  1. Configure the agent workflow and its integration settings.
  2. Inspect execution logs and parallel queues to follow processing.
  3. Review expense details, separate FI/HCM posting states, and business messages.
  4. Follow the related accounting, HCM, or IDoc record to investigate the workflow's interactions with SAP.

03 · Commercial application

A supplier workspace from order to invoice

I built a supplier self-service application sold to multiple Italian customers in aviation, pharmaceuticals, and retail. Suppliers use it to confirm purchase orders, submit delivery notices, and prepare invoices against received quantities.

The screenshots show this app using sample data. Customer identities are confidential.

Problem
SAP transactions were too difficult for most end users. Customers needed a simpler, responsive interface for everyday tasks.
My work
Designed and built a responsive SAPUI5 application with simpler flows for purchase-order confirmations, delivery notices, and invoices.
Result
End users have a simpler interface for everyday supplier tasks that adapts to their screen. The application was sold to multiple Italian customers across aviation, pharmaceuticals, and retail.
Supplier workflowOrder confirmations, delivery notices, invoices, and processing feedback.
  1. Review and confirm an order, then submit a partial delivery notice.
  2. Prepare an invoice against quantities recorded as received by the buyer.
  3. Follow document acknowledgements and processing exceptions.
