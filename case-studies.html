01 · Architecture and implementation

Faster, more reliable SAP-to-SaaS synchronization

A redesign of the synchronization layer between a SaaS product and its customers’ SAP systems.

Problem
Slow loads, failures without retries, missed future-dated updates, and unchanged data sent repeatedly to the SaaS API.
My work
Rebuilt data access around SAP interfaces and ordered parallel queues, with retries, version handling for current and future periods, caching, and PUT change detection.
Result
Faster loads, recovery after temporary failures, and less service and middleware traffic. SAP interfaces replaced direct database reads.

Download the before-and-after comparison (SVG)

How synchronization worksDependencies, retry behavior, and PUT change detection.

Initial and delta loads, especially for materials and invoices, were slow. Temporary errors failed entire units, future-dated versions were missed, and unchanged updates increased service load and middleware costs.

  1. BAPI, IDoc, output messages, BOR, and CDS views feed the object queues.
  2. A queue can contain multiple object types. In this example, the supplier resolves before the purchase order in the same queue.
  3. A failed unit retries in place and blocks later units in that queue. Independent queues can continue.
  4. Successive field or version changes to one object remain ordered, as shown by the cost-center example.
  5. Before a PUT, compare the object's payload hash with its last successful outbound update. Identical content skips the request and completes the unit. Changed content or a missing baseline sends the PUT.
  6. A successful PUT saves the new hash. Failure retains the previous baseline so the update remains eligible for retry. Other HTTP methods bypass this PUT-specific check.

The diagram illustrates processing behavior. Queue allocation, retry timing, and the hash algorithm depend on the implementation.

The Clean Core change shown here is replacing direct database reads with SAP interfaces. API choices and release status depend on the target SAP system.

In a separate SAP integration project, parallel processing, queues, caching, and hashing delivered at least 5× the throughput of the previous monolithic implementation. That comparison depends on customer system capacity and allocated resources.

02 · Agentic expense workflow

Clear visibility into expense agent actions

Supporting agentic AI transformation with SAP workflow configuration, execution tracking, and posting visibility.

Problem
The agentic SaaS worked as intended, but the customer had no clear view of the agent’s actions or their status in SAP.
My work
Built workflow configuration, execution logs, expense details, and queue and FI/HCM status views, with direct links to the related SAP records.
Result
Customers can see which actions are complete, which are still processing, and which need attention.
Workflow configuration and execution trackingAgent settings, execution logs, queues, and SAP processing outcomes.
  1. Configure the agent workflow and its integration settings.
  2. Inspect execution logs and parallel queues to follow processing.
  3. Review expense details, separate FI/HCM posting states, and business messages.
  4. Follow the related accounting, HCM, or IDoc record to investigate the workflow's interactions with SAP.

03 · Commercial application

A simpler, responsive supplier workspace

A supplier self-service app sold to multiple Italian customers in aviation, pharmaceuticals, and retail.

The screenshots show this app using sample data. Customer identities are confidential.

Problem

My work
Designed and built the SAPUI5 interface for confirming purchase orders, submitting delivery notices, and invoicing.
Result
End users can handle routine supplier tasks in a simpler interface on desktop or mobile.
Supplier workflowOrder confirmations, delivery notices, invoices, and processing feedback.

  2. Prepare an invoice against quantities recorded as received by the buyer.
  3. Follow document acknowledgements and processing exceptions.
